### 1.3 术语

| 术语 | 含义 |
|---|---|
| 线程 | 可被调度的执行上下文：入口函数 + 自己的内核栈 + 保存的寄存器状态 |
| 就绪队列 | 可以运行的线程的 FIFO 列表；正在运行的线程不在其中 |
| 空闲线程 | 就绪队列为空时运行的线程，它执行 `hlt` |
| 引导上下文 | 线程 0：`kernel_main` 自身所运行的那个上下文，使用引导器给的栈 |
| tick | 一次 PIT 中断，也就是一次调度机会 |
| IST | Interrupt Stack Table：TSS 中供指定向量切换使用的栈 |
| 临界区 | 在中断关闭（`IF = 0`）下执行的区间 |

## 2. 基线与前置条件

M3 使用 M2 的 `memory::MemoryLayout`（页帧 + 堆）与 M1 的 IDT/异常/日志设施。不得破坏的约定：

* `BootInfo` 与入口 ABI 不变；M3 不新增 `BootInfo` 字段；
* 退出码 33/35/37/39/41/43 含义不变；45 是新增（§9.1）；
* 引导器不变（内核镜像仍在 `MAX_KERNEL_PAGES = 256` 之内）；
* 内核依旧不碰 MMIO（§4.1 说明 M3 如何做到不需要它）。

> ⚠️ **M2 的决策 #20 到此结束。** `memory_subsystem_CN.md` §5.4 写着「不加锁；启用中断或第二个核
> 之前必须加锁」。M3 启用中断，因此那把锁就在 M3 补上——页帧分配器、堆与调度器状态（§5）。

## 3. 描述符表：GDT、TSS、IST

M1 刻意运行在固件的 GDT 上、且不装 IST（当时的决策记录写着「留到用户态之前」）。M3 装上自己的，
因为抢占会把三重故障的代价放大：当内核栈本身不可用时发生的 `#DF`，正是 IST 存在的意义
［决策 #26］。

* 静态 GDT 共 6 项：null、内核代码（64 位，DPL 0）、内核数据（DPL 0）、16 字节的 TSS 描述符；
  另留两个空槽给 M4 的用户代码/数据，这样将来新增段不会移动已有选择子；
* 选择子沿用惯例的 `0x08`（代码）与 `0x10`（数据），因此 `lgdt` 之后重新装载 `CS`/`SS`/`DS`/`ES`
  仍然保持正在执行的代码有效；
* TSS 里保存 `rsp0`（只有在从 CPL 3 进入中断时才会用到——那是 M4）与两个 IST 栈：
  **IST1 给 `#DF`（向量 8）**、**IST2 给 NMI（向量 2）**。每个 IST 栈是从页帧分配器取的一页，
  带与线程栈相同的金丝雀（§6.2）；
* IDT 中 `#DF` 与 NMI 的门设置 IST 索引；其余所有门保持 IST 0（使用当前栈）。

`lgdt` 之后内核会用 `sgdt` 断言读到的是我们自己的表，并断言 `CS`/`SS` 仍携带预期的选择子。GDT
装错会立即三重故障，所以这条断言不是可选项。

## 4. 中断基础设施

### 4.1 选 8259 PIC + PIT，而不是本地 APIC —— 这是刻意的
`memory_subsystem_CN.md` §3.4 明确写着 M2 **不映射任何 MMIO**，且之后任何要碰本地 APIC 的里程碑
都必须先补显式映射。而传统的 8259 PIC（`0x20`/`0x21`、`0xA0`/`0xA1`）与 PIT（`0x40`–`0x43`）
**只用端口 I/O**，于是 M3 能在完全不动分页设计的前提下拿到时钟中断［决策 #24］。APIC 是独立的
后续改动（它还需要决定 MMIO 的映射与缓存属性）。

* 把主片重映射到向量 `0x20..0x27`、从片到 `0x28..0x2F`（ICW1–ICW4），因为固件把它们留在
  `0x08..0x0F`，会与 CPU 异常冲突；
* **屏蔽除 IRQ0（时钟）之外的所有 IRQ**；从片整体屏蔽；
* 把 PIT 通道 0 设为模式 3（方波），分频值 `1193182 / 100 = 11932`，即 `TIMER_HZ = 100`
  （分频值必须取整，因此实际频率是 99.9984 Hz；这一点如实写出来，不假装精确）；
* 调度器状态里维护单调递增的 tick 计数（§8.3）。

### 4.2 向量分配

| 向量 | 来源 | 处理器 |
|---|---|---|
| 0..31 | CPU 异常（M1） | `exception_handler` → 诊断 → 41 |
| 2（NMI） | NMI | 在 IST2 栈上；诊断 → 41 |
| 8（`#DF`） | 双重故障 | 在 IST1 栈上；诊断 → 41（这正是 IST 的意义） |
| 0x20 | IRQ0 / PIT | `timer_tick` → 计数、可能重调度（§7.3）→ EOI |
| 0x21..0x2F | 其它 IRQ | 已屏蔽，不会到达；门指向「伪中断」处理器，只打印并 EOI（防御性） |

### 4.3 中断处理器必须遵守的规则
1. **绝不分配内存。** 在 ISR 里取堆锁是安全的（此时中断本就关闭），但 M3 不要"在 ISR 里分配"
   这种策略；处理器必须无分配。
2. **绝不 yield、绝不阻塞、绝不自行切换。** ISR 唯一可能发生的切换是调度器决定的那个（§7.3）。
3. **必须 EOI** PIC（在切换决策之后、`iretq` 之前），否则 IRQ0 不再到来。
4. 全程使用中断门（进入时 `IF = 0`），因此处理器不会嵌套。

## 5. 锁

### 5.1 锁本体
`crates/kernel/src/lock.rs` 提供**中断安全自旋锁**：

```rust
pub struct SpinLock<T> { locked: AtomicBool, value: UnsafeCell<T> }
impl<T> SpinLock<T> {
    pub const fn new(value: T) -> Self;
    pub fn lock(&self) -> SpinLockGuard<'_, T>;   // 先 cli，再自旋抢标志
}

pub struct CriticalSection { /* 保存的 RFLAGS.IF */ }
pub fn critical() -> CriticalSection;             // cli，并记住 IF 原本是否置位

/// 当前线程持有的锁数量；yield/exit 用它拒绝"持锁切换"。
pub fn held_count() -> usize;
```

顺序很重要：**先关中断，再抢标志。** 反过来会留下一个窗口：中断处理器可能看到锁已被占用，而持有者
其实还没真正进入临界区。

`SpinLockGuard` 创建时把 `held_count` 加一、析构时减一；析构同时释放标志并恢复保存的 `IF`。

### 5.2 什么被什么保护
| 状态 | 保护方式 |
|---|---|
| 调度器状态（线程表、就绪队列、当前线程、tick） | `critical()` —— 单核上 `IF = 0` **就是**调度器的锁（§5.3），因为调度器也会从时钟 ISR 里被修改，那里用自旋锁会死锁 |
| 内核堆（`#[global_allocator]`） | 空闲链表外的一把 `SpinLock` |
| 页帧分配器 | 位图外的一把 `SpinLock` |

### 5.3 调度器为什么用 `IF = 0` 而不是用锁
时钟 ISR 必须能重调度。如果调度器由自旋锁保护：持锁线程在**没**持堆锁时会被抢占（中断是开的），
ISR 于是尝试获取同一把锁，而单核自旋锁无法前进 → 死锁。

因此规则是：**调度器状态只在 `critical()` 区间里被触碰**——也就是中断关闭，因此时钟不可能插入。
这让调度器的临界区在构造上不可抢占。

由于锁不会跨切换持有，"切换之后由谁解锁"的问题根本不存在。让这一切成立的不变量是：

> **每一次上下文切换都发生在 `IF = 0` 之下，并且由恢复执行的那个上下文负责恢复 `IF`**（线程的
> `CriticalSection` 守卫，或 ISR 的 `iretq`）。

因此在 `switch` 内部被恢复的线程，总是从"中断关闭"的那一点继续，并且恰好在自己关中断的那条路径上
重新打开一次。

### 5.4 唯一会死锁的事
跨上下文切换持有堆/页帧锁：另一个线程拿到 CPU 后，会永远自旋在一把只有被换出的那个线程才能释放的
锁上。M3 把它变成**panic（退出码 41）**而不是挂死：`yield()` 与 `exit()` 断言
`held_count() == 0`。这条检查本身也是自检证据的一部分（§10）。

## 6. 线程模型

### 6.1 线程是什么
* **入口函数** `extern "C" fn() -> !`；若它返回，蹦床会替它调用 `exit`；
* **自己的内核栈**，来自页帧分配器：`THREAD_STACK_PAGES = 4`（16 KiB），页对齐；
* **保存的寄存器状态**（§7）；
* **状态**：`Unused`、`Ready`、`Running`、`Exited`；
* id：固定表（`MAX_THREADS = 16`）中的 `usize` 下标。

所有线程**共享同一个地址空间**——M2 建立的恒等映射页表。M3 没有按线程的 `CR3`［决策 #25］；
那要等到用户态（M4），在那里它不可避免。

### 6.2 栈、金丝雀，以及不设防的部分
* 栈是从页帧分配器取的 `THREAD_STACK_PAGES` 个页帧，创建时在**最低 8 字节**写入**金丝雀字**，
  回收时检查；
* M3 **没有保护页**：恒等映射在 2 MiB 以上用 2 MiB 大块，取消映射单个 4 KiB 页意味着拆分大块并
  分配页表——那是对分页接口的改动，本里程碑不需要［决策 #32］。因此"跳过金丝雀的溢出"（大块
  `memcpy`、深递归）仍然可能发生；金丝雀抓的是常见情况；
* 空闲线程的栈与两个 IST 栈以同样方式分配；**引导上下文（线程 0）使用引导器的栈**，其页帧永不释放
  （§6.4）。

### 6.3 生命周期

```
                create()                schedule()                exit()
   Unused ──────────────▶ Ready ──────────────────────▶ Running ──────────▶ Exited
                            ▲                              │                  │
                            └──────── 抢占 / yield ────────┘                  │
                                                                              ▼
                                                                    由调度器回收
                                                                    （状态 → Unused，释放栈）
```

* `create(entry)` 分配栈、写入金丝雀、构造初始上下文，并把线程追加到就绪队列；失败（没有空槽、
  没有页帧）以 `Err` 返回给调用方；
* `exit()` 把当前线程标为 `Exited`，然后**永远**切换走；调度器稍后回收它（§8.3）——线程永远不能
  释放自己正踩着的栈；
* 从入口函数返回等同于退出（蹦床调用 `exit`）；
* `Exited` 线程不再被调度；它的 `ThreadId` 只有在回收之后才可复用。

### 6.4 线程 0：引导上下文
`kernel_main` 运行在引导器给的栈上、中断关闭，因此它**本身**就是一个可以被换出再换回的上下文。
M3 把它登记为**线程 0（"boot"）**：

* 它的"入口"是 `kernel_main` 的剩余部分——它永远不会经由蹦床被"启动"；
* 它的栈来自 `BootInfo`，永不释放；
* 它像其它线程一样参与调度（在自旋时也会被抢占，§10.4）；
* 它结束时关闭中断并退出机器（§9）。

## 7. 上下文与上下文切换

### 7.1 `Context`
```rust
#[repr(C)]
pub struct Context {
    pub rsp: u64,       // 保存的栈指针（指向保存的 rbx/rbp/r12-r15 与返回地址）
    pub thread: u32,    // 自检与诊断用
    pub _pad: u32,
}
```
线程其余的寄存器状态**在它自己的栈上**，这正是切换可以做得很小的原因：被调用者保存寄存器与恢复地址
在交换 `rsp` 之前被压进各自的栈。

### 7.2 切换 ABI
```rust
/// # Safety
/// `from`/`to` 必须指向各自线程的 `Context`，且必须在 `IF = 0` 下调用。
pub unsafe fn switch(from: *mut Context, to: *const Context);
```
`switch` 约 15 条指令：压 `rbx`、`rbp`、`r12`–`r15`；把 `rsp` 存入 `*from`；从 `*to` 取 `rsp`；
弹 `r15`–`rbx`；`ret`。那个 `ret` 返回到该栈上最后一次调用 `switch` 的位置［决策 #28］。

几个要紧的推论：

* 被换出的线程是在**它自己那次 `switch` 调用内部**被恢复的，所以在 Rust 看来 `switch` 只是"花了
  一会儿"；
* **切换绝不在持锁时发生**（§5.4），且始终在 `IF = 0` 下；
* `switch` 必须在**当前**线程的栈上调用；它不可重入、也不能被两处同时调用（单核：由 `IF = 0` 保证）。

### 7.3 谁调用 `switch`
| 路径 | 发起者 | 说明 |
|---|---|---|
| 协作式 | 线程调用 `yield()` | `critical()` + 调度决策 + `switch`；线程被恢复后由守卫恢复 `IF` |
| 抢占式 | 时钟 ISR | `critical` 是隐含的（门已清 `IF`）；处理器计 tick、询问调度器并切换；切换返回后 EOI，桩 `iretq` 恢复 `IF` |
| 退出 | 线程调用 `exit()` | 标记 `Exited` 后切换走；永不返回 |
| 启动 | 调度器 | 切到一个全新线程时，"返回"进入蹦床而不是上一次的 `switch` 调用 |

### 7.4 启动一个新线程
初始栈被构造成让 `switch` 的弹栈/`ret` 落在 `thread_trampoline`，线程的入口点与参数放在蹦床会去读
的位置：

* 栈内容自上而下依次是：**FXSAVE 区**（§7.5）、蹦床返回地址、六个占位的被调用者保存槽，然后是
  入口函数指针与蹦床读取的一个槽；
* 进入蹦床时 `rsp` 满足 `rsp % 16 == 8`，与真的发生过一次 `call` 完全一致，因此蹦床可以直接调用
  Rust 代码而不必重新对齐；
* 蹦床读出入口函数、调用它，若它竟然返回则调用 `exit()`。

### 7.5 XMM 状态：存在线程自己的栈上，而不是每线程一个 FXSAVE 区
内核并非"与浮点无关"：编译器可能为大结构体搬移和类 `memcpy` 循环使用 XMM 寄存器，而源码里完全
看不出来。被抢占线程的 XMM 若被接替者破坏，会造成**非确定性**的数据损坏——最糟的一类 bug。因此 M3
显式处理 XMM［决策 #27］：

* **时钟 ISR 桩**在任何 Rust 代码之前执行 `fxsave`，写到当前线程的栈上（16 字节对齐、位于保存的
  GPR 帧之下）；
* **ISR 收尾**在恢复 GPR 之前从同一位置执行 `fxrstor`，于是切换后恢复执行的线程拿回自己的 XMM；
* **不需要每线程 FXSAVE 区**：线程的 XMM 状态与它的 GPR 一样就在自己栈上。新线程的构造栈里放一块
  清零的区，并把 `MXCSR` 置为 `0x1F80`（标准默认值）；
* 协作式 `yield()` 路径完全不需要处理 XMM：在函数调用边界上 XMM 是调用者保存（已死），没有东西
  需要保留。

被否决的替代方案是"内核线程不许用 SSE"——但决定何时使用 XMM 的是编译器，不是程序员。

## 8. 调度器

### 8.1 策略
在 FIFO 就绪队列上做**严格轮转（round-robin）**［决策 #31］：

* 就绪队列是容量 `MAX_THREADS` 的 `ThreadId` 环形缓冲；
* 当前线程被抢占或调用 `yield` 时，它被追加到**队尾**，队首被弹出成为新的运行线程；
* 若队列为空且当前不是空闲线程 → 切到**空闲线程**；若已经在空闲线程上 → 保持（它执行 `hlt`，
  因此空闲机器不烧 CPU）；
* 空闲线程**不在**就绪队列里，也永不被回收；
* 优先级、截止期、公平性记账与负载均衡明确不在范围内；它们属于后续里程碑，需要自己的文档。

### 8.2 逻辑放在哪里
`crates/kernel-sched`（新增，零依赖、`no_std`、`#![forbid(unsafe_code)]`）持有纯状态机：线程表、
就绪队列、tick 计数、`create`/`exit`/`yield`/`pick_next` 决策与回收候选清单。它作用于内核交给它的
存储（与 `kernel-memory` 对位图的做法完全一致），因此可以被宿主单元测试覆盖。一切需要 CPU 的东西
——`switch`、端口 I/O、`fxsave`、IDT——都留在 `crates/kernel`。

### 8.3 tick 记账与回收
* 每次时钟中断在临界区内把 tick 计数加一；
* 调度器返回一个决策：`Keep`（不切换）或 `Switch(ThreadId)`；
* 切换之后调度器扫描 `Exited` 线程，把它们的栈列为可回收；内核释放那些页帧并把槽位重置为
  `Unused`。线程自己的栈绝不在它还在运行时被释放，因为 `exit` 会先切换走（§6.3）。

## 9. 内核入口、退出协议与退出码

### 9.1 新增退出码

| 退出码 | 含义 | 报告者 | 状态 |
|---|---|---|---|
| **45** | **内核调度自检失败** —— 线程无法创建、轮转顺序不对、被抢占的线程没有取得进展、锁未提供互斥、或栈金丝雀被破坏 | 内核 | M3 新增 |

41 仍是"内核崩了"（CPU 异常或 panic）；43 仍是"内存初始化失败"。三者负责人不同，这正是把它们分开
的意义。

### 9.2 中断开关时间线
1. M0 到 M2 的一切照旧在 `IF = 0` 下运行；
2. GDT/TSS/IST、PIC、PIT 与调度器都在 `IF = 0` 下初始化；
3. `sti` **只发生一次**，就在创建第一个非引导线程之前——也就是在中断处理器可能触碰的每个子系统
   都就绪之后；
4. 自检在中断开启下运行（必须如此：它要测抢占）；
5. 退出协议在报告之前重新关闭中断。

### 9.3 退出协议
自检通过后：`cli` → 屏蔽 IRQ0（PIC）→ 断言就绪队列为空、除引导上下文外没有 `Running` 线程 →
打印摘要 → 写退出端口（37）。如果在仍有可运行线程时走到 `finish()`，那就是内核 bug，因此这条断言
是协议的一部分，而不是一句注释。交互模式（`exit_port == 0`）下内核改为在中断关闭下 `hlt` 停机，
模拟器仍然可用。

## 10. 自检（把证据变成可机器校验的东西）

在 M2 的内存自检之后、于 `kernel_main` 中运行，此时中断已开启。每一步都打印结果；失败以 **45**
退出，并带上步骤号、被破坏的不变量与相关地址/数据。

1. **互斥** —— 4 个线程各自在锁下把共享计数器加 2000 次（用与堆锁同款 `SpinLock`，但为本测试单独
   实例化）。最终值必须恰好是 8000；临界区内被抢占导致的丢失更新会立刻暴露。
2. **轮转顺序（协作式）** —— 3 个线程各自把 id 追加到共享字节数组、然后 `yield()`，共 10 轮。观察到
   的序列必须恰好是 `012012…`；任何偏离（某线程连续跑两次、漏唤醒）都判失败。
3. **抢占** —— 线程 **A** 忙等（从不 yield）一个只有线程 **B** 能设置的标志，并带 tick 预算上限。
   只有时钟抢占 A，B 才可能运行——这正是要证明的事：若抢占失效，A 永远看不到标志，预算耗尽后干净地
   判失败（45），而不是挂死。
4. **tick 在推进** —— 第 3 步期间 tick 计数必须至少推进过 A 观察到的切换次数；PIT 卡死会让计数器
   停在 0，在这里失败，而不是超时。
5. **退出、回收与记账** —— 所有测试线程退出；此后调度器中不得留有 `Exited` 线程，每个栈金丝雀必须
   完好，页帧分配器的空闲数必须回到创建线程之前的值，且唯一 `Running` 的必须是引导上下文。
6. **持锁纪律** —— 每个调度点上 `held_count()` 都必须为 0；自检还会直接验证守卫的记账：取测试锁时
   必须报告 1（也就是说此刻 `yield` **会**被拒绝），释放后重新报告 0。那条 panic 路径本身
   （持锁 `yield` → 41）**刻意不触发**，因为自检失败必须以 45 报告，而不是崩溃。

两个仅测试特性让失败可以被真正触发，而不是停留在理论上［决策 #35］：

| 特性 | 效果 | 期望 |
|---|---|---|
| `inject-no-preempt` | 时钟照常计数，但调度器永不切换到别的线程 | 自检第 3 步失败 → **45** |
| `inject-double-fault` | 调度器就绪后执行 `int $8` | `#DF` 门切到 IST1，处理器报告并以 **41** 退出；若变成三重故障则表现为超时（124）或重启，也就是可见的失败 |

### 11.4 已知坑（按可能性排序）

| # | 坑 | 对策 |
|---|---|---|
| 1 | GDT 写错会立刻三重故障 | `lgdt` 之后先用 `sgdt` 自断言、再校验选择子，然后才做别的事（§3） |
| 2 | PIC 未重映射 → 时钟与异常向量撞车 | 先重映射、只留 IRQ0，并断言未屏蔽的 IRQ 从不出现 |
| 3 | 忘了 EOI → 只有一次 tick | 处理器里 EOI，由自检核对（tick 必须持续增长） |
| 4 | 持锁时切换 → 单核死锁 | `held_count` panic + 「`IF = 0` 就是调度器的锁」这条规则（§5.4） |
| 5 | 抢占时 XMM 被踩 | 时钟桩里在本线程栈上 `fxsave`/`fxrstor`（§7.5） |
| 6 | 线程启动时栈对齐错 → 第一条 `movaps` 就 `#GP` | 构造栈让蹦床看到 `rsp % 16 == 8`，蹦床再自查一遍 |
| 7 | 线程还在自己栈上跑就释放它 | `exit` 先切换走；只有调度器回收（§6.3） |
| 8 | 从不 yield 的线程把机器挂死 | 抢占检查带 tick 预算上限，失败报 45（§10.3） |
| 9 | 线程正处于 `switch` 中途时 ISR 又进入 `switch` | 整个切换期间 `IF = 0`，且时钟门不嵌套（§4.3） |
| 10 | 把 PIT 分频当精确值 | 文档写明 99.9984 Hz；自检从不假设精确频率 |

## 12. 决策记录

| # | 决策 | 结果 | 理由 | 可逆性 |
|---|---|---|---|---|
| 24 | M3 一开始就做抢占式调度，由 8259 PIC + PIT 驱动 | 纯端口 I/O、100 Hz，外加协作式 `yield` | 没有抢占的调度不算调度，而 M4 本来就需要时钟抢占；PIC/PIT 避开了本地 APIC 必然引出的「不映射 MMIO」问题 | 中（日后由 APIC 取代） |
| 25 | 内核线程共享单一地址空间 | 线程 = 入口 + 栈 + 保存的寄存器；无按线程 `CR3` | 这是"单核内核线程骨架"该有的体量；按线程的地址空间属于用户态，硬件在那里才强制要求 | 高 |
| 26 | M3 就装自己的 GDT + TSS + `#DF`/NMI 的 IST | 6 项 GDT、两个 IST 栈 | 抢占让"栈不可用时的双重故障"更可能出现，而 IST 把静默的三重故障重启变成可诊断的崩溃 | 高 |
| 27 | XMM 存在线程自己的栈上，由时钟 ISR 路径保存 | 桩里 `fxsave`/`fxrstor`；`yield` 路径什么都不做 | 决定何时用 XMM 的是编译器而不是程序员；而每线程 FXSAVE 区是多余的，因为栈本来就保存了线程状态 | 高 |
| 28 | `switch(from, to)` 压栈/弹栈式，新线程用构造栈引导 | 约 15 条指令汇编；恢复发生在自己那次 `switch` 调用内部 | 最小且正确的机制；统一了 yield、抢占与线程启动 | 中（属 ABI 级细节） |
| 29 | `IF = 0`（`CriticalSection`）就是调度器的锁；堆与页帧分配器用中断安全 `SpinLock` | 任何锁都不跨切换持有 | 单核上被调度器持有的自旋锁，会在时钟抢占持锁者时死锁；而 `IF = 0` 不会 | 中 |
| 30 | 中断处理器不分配、不阻塞；持锁 `yield`/`exit` 直接 panic | `held_count` 在每个调度点被检查 | 把 M3 唯一可能产生的死锁变成响亮且可测试的失败 | 高 |
| 31 | FIFO 就绪队列上的严格轮转 | 被抢占/yield 的线程去队尾 | 骨架应当是"仍然公平"的最简方案；优先级属于后续里程碑自己的接口 | 高 |
| 32 | 不设保护页，改用金丝雀 | 4 页栈 + 回收时检查金丝雀 | 保护页需要单页取消映射，而那需要在分页接口里拆分大块——超出本里程碑 | 高 |
| 33 | 线程 0 是运行在引导器栈上的引导上下文 | 永不释放、永不经由蹦床启动 | `kernel_main` 本身就是一个上下文；把它包起来零成本，还能让切换路径保持统一 | 高 |
| 34 | 调度自检失败用新退出码 45 | 与 39/41/43 区分 | "调度器行为错误"既不是契约破损、也不是崩溃、也不是内存失败 | 中（已发布的含义冻结） |
| 35 | 注入：`inject-no-preempt` → 45，`inject-double-fault` → 41 | 两者都能从 `tests/smoke.sh` 触发 | 最值得否证的两条主张是"时钟真的会抢占"与"`#DF` 会落在 IST 上而不是三重故障" | 高 |

## 13. 接口变更流程
1. `crates/kernel-sched` 的公开项是内核与其自身逻辑之间的接口；改动必须配套宿主测试。
2. 任何改动**引导器↔内核**契约（`BootInfo`、入口 ABI、退出码）的变更，遵循
   `kernel_interface_CN.md` §11。
3. 上下文切换 ABI（§7）是内部的，但具有 ABI 性质：改动它必须同时改 `thread.rs`、蹦床与 ISR 桩。
4. 双语文档：每次改动必须同时更新本文件与 [threads_and_scheduling.md](threads_and_scheduling.md)
   （AGENTS.md 第 4 条）。
5. 实现状态：每完成一部分，更新 §11 与 `kernel_interface_CN.md` §9 的 M3 行。
